# v13：饮食照片自动分析与平铺字段

## 用户路径

选择照片/拍摄 -> 解码并剥离元数据 -> 等比例预览 -> 百炼视觉 -> 回填可编辑字段 -> 用户确认 -> 原来的小猫书写/庆祝/数据回顾。
饮食不再创建 `#analyze-photo`；面部仍创建该按钮。本轮不更换全局布局或角色素材。
四项营养直接是 `#entry-form` 的 `.field` 子节点。`group` 仅是兼容既有数据定义的内部元数据。

## 分析任务

`acceptPhoto` 是自动分析的唯一用户选图入口，`showPhoto` 只渲染。
`photoJob` 内存状态包括 selected、waiting-key、running、done、needs-info、failed、canceled。
同一已经完成的照片和未变表单不重复请求。修改后显式选图、失败/信息不足后点击小猫可以重试。
不在 input/resize/语言切换时自动发模型请求。
首次未配置 Key 的选图保留为 waiting-key；用户启用后只恢复仍属于当前表单的那一张。

返回使用照片字节身份、类别、记录日期、编辑条目ID、递增serial、AbortSignal六项检查。
切页、切日、清除Key、移除/更换照片或短按取消，都阻止迟到回填。摄像头取到画面后立即关闭轨道。
文件读取只生成候选JPEG，不在接受之前改变当前照片，避免取消后迟到解码污染当前图片。

## 字段所有权

`photo-draft.js` 的纯函数按字段值与版本号追踪来源。
上传前已有的手动文字或数值均优先。等待期间输入、删除、甚至删后改回同值仍视为用户修改。
换图/移除时只清除上张照片自动填入、且值和版本都未变的字段，不删用户手动调整，也不修改历史记录。
重试时可更新同张图片仍拥有的字段，但不能覆盖用户修正后的内容。
数据保存仍由原确认动作执行；每次分析不产生新记录、不触发庆祝、不增加首页计数。

## 提示词与数值

允许清楚菜品按常见份量与配方给出总量，不把没有秤当作唯一拒绝理由。
单餐总热量为 kcal，蛋白质/碳水/脂肪为 g，输出单个数值而非范围，目测结果适度取整。
用户指定的份量、比例和数值优先；不把共享整桌当作一个人全部吃掉。
无食物、空盘、严重遮挡等情况下未知字段仍留空；不把null转成0。餐次与主观备注不得从图片猜测。
内部 `estimated` 保留，常驻界面不显示黄色说明或“营养信息·估算”外框。
实际问题在小猫气泡短句提示；不展示原始服务端错误或带敏感信息的正文。

## 本轮验证

单元测试验证字段所有权、手动修改保护、数值空值/范围、提示词约束及原有全量逻辑。
`v13-browser.py` 使用交付HTML/CSS/JS、真实文件input和合成视频捕获路径；网络响应是测试替身。
覆盖自动一次请求、Key后置启用、取消、乱序返回、六种窗口尺寸、重试、信息不足、面部回归、中英文状态。
`v12-browser.py` 重跑语音/接口/回顾的既有故障恢复；饮食测试入口更新为新选图逻辑。
本轮没有用个人API或实体麦克风/摄像头检验；模型结果准确度不能由固定回复测试证明。
